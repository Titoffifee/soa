## 2. Домены и зона ответственности

| Домен | Ответственность |
|---|---|
| Identity & Users | Регистрация, аутентификация, профили покупателей и продавцов, роли, JWT. |
| Catalog | Карточки товаров, категории, медиа, остатки, поиск и фильтрация. |
| Ordering | Создание заказа, корзина, статусы заказа, история. |
| Payments | Инициирование оплаты во внешнем платёжном шлюзе, обработка вебхуков, рефанды, реестр транзакций. |
| Notifications | Подписка на доменные события и доставка email, SMS, push с шаблонами. |
| Personalization / Feed | Сбор поведенческих событий, построение и ранжирование персональной ленты товаров. |

---

## 3. Распределение доменов по сервисам

Применяем принцип: один ограниченный контекст — один сервис.

| Сервис | Домен | Почему именно так |
|---|---|---|
| `user-service` | Identity & Users | Чувствительные данные, отдельный SLA, своя БД, отдельный жизненный цикл. |
| `catalog-service` | Catalog | Высокая read-нагрузка, поисковый индекс, своя схема данных, отдельное горизонтальное масштабирование. |
| `order-service` | Ordering | Транзакционная логика, оркестрация шагов оформления, разная частота релизов. |
| `payment-service` | Payments | Регуляторика, изоляция от остального кода, общение с внешним PSP. |
| `notification-service` | Notifications | Чисто event-driven, не лежит на критическом пути заказа, может лагать. |
| `feed-service` | Personalization / Feed | Другой стек Python и ML, другая БД, асинхронные пересчёты. |
| `api-gateway` | Cross-cutting | Не домен, а инфраструктурный слой: TLS, JWT, rate-limit, маршрутизация. |

Логика разбиения:

1. Bounded Context из DDD: каждый домен имеет свой язык и модель.
2. Разные нефункциональные требования: каталог read-heavy, заказы транзакционные, фид ML и batch.
3. Изоляция отказов.
4. Каждый сервис может иметь свою команду.

## 4. Границы владения данными

Принцип: каждый сервис владеет своей БД, никто извне не ходит в неё напрямую. Доступ только через API сервиса-владельца или через события.

| Сервис | Владеет данными | Зона ответственности |
|---|---|---|
| `user-service` | `users`, `roles`, `sessions` | Source of truth по личности пользователя. |
| `catalog-service` | `products`, `categories`, `stock` + поисковый индекс | Source of truth по товарам и остаткам. |
| `order-service` | `orders`, `order_items`, `status_history` | Source of truth по заказам. |
| `payment-service` | `payments`, `transactions`, `refunds` | Source of truth по платежам. |
| `notification-service` | `templates`, `delivery_log`, `user_prefs` | Source of truth по доставке уведомлений. |
| `feed-service` | поведенческие события, кэш ленты | Аналитическое хранилище, derived data. |

Нет общих БД. Если сервису нужны чужие данные:

- В реальном времени: синхронный gRPC-вызов к владельцу.
- Для собственной модели или витрины: подписка на доменные события и построение локальной read-model в стиле CQRS. Например, `feed-service` строит свою копию метаданных товаров.

### Взаимодействия сервисов

| От и кому | Тип | Способ | Зачем |
|---|---|---|---|
| `order-service` → `catalog-service` | sync | gRPC | Проверка наличия и резерв товара при оформлении. |
| `order-service` → `user-service` | sync | gRPC | Валидация покупателя. |
| `payment-service` → `order-service` | sync | gRPC | Подтверждение заказа после оплаты. |
| `feed-service` → `catalog-service` | sync | gRPC | Дообогащение карточек товаров. |
| `order-service` → Kafka | async | event | Публикация `OrderCreated`, `OrderCancelled`. |
| `payment-service` → Kafka | async | event | `PaymentCompleted`, `PaymentFailed`. |
| `catalog-service` → Kafka | async | event | `ProductUpdated`, `StockChanged`. |
| `user-service` → Kafka | async | event | `UserRegistered`. |
| Kafka → `notification-service` | async | subscription | Триггеры писем и пушей. |
| Kafka → `feed-service` | async | subscription | Сигналы для пересчёта ленты. |
| Kafka → `payment-service` | async | subscription | Инициирование оплаты после `OrderCreated`. |
| `payment-service` → Payment Gateway | sync | HTTPS | Внешний платёж. |
| `notification-service` → Notification Provider | sync | HTTPS | Внешняя доставка. |

Правило: критический путь оформления синхронный, всё остальное (уведомления, аналитика, лента) асинхронное.

## 5. Альтернативные варианты декомпозиции

### Вариант A. Модульный монолит

Один деплоймент, внутри модули по доменам, одна БД с разделением по схемам.

- Плюсы: минимальная инфраструктура, простые транзакции на одной БД, самый быстрый старт, легче отлаживать.
- Минусы: совместное масштабирование, нельзя дёшево скейлить только каталог, один тех-стек на всё, деплой это риск для всех модулей, границы доменов со временем размываются.

### Вариант B. Coarse-grained сервисы, 3 или 4 сервиса

Объединяем близкие домены: `commerce-service` с Users, Catalog и Orders, `payment-service`, `comms-service` с Notifications и Feed, Gateway.

- Плюсы: меньше сетевых вызовов и операционной сложности, проще консистентность внутри `commerce`, меньше Kafka-топиков.
- Минусы: `commerce-service` становится мини-монолитом, read-heavy каталог и транзакционные заказы делят один рантайм и одну БД и конкурируют за ресурсы, объединение Feed на Python и Notifications на Go натягивает разные стеки в один сервис.

### Вариант C. Fine-grained микросервисы по bounded context (наш выбор)

7 сервисов: `api-gateway`, `user`, `catalog`, `order`, `payment`, `notification`, `feed` плюс Kafka.

- Плюсы: независимое масштабирование и деплой, изоляция отказов, разные стеки и БД под задачу, чёткие границы владения данными, изоляция `payment`.
- Минусы: дороже инфраструктурно, требуются Kafka, service mesh, observability, eventual consistency между сервисами, нужны saga и outbox, сложнее локальная разработка и end-to-end тесты, выше cognitive load.

### Сводная таблица trade-off

| Критерий | A. Монолит | B. Coarse | C. Fine |
|---|---|---|---|
| Скорость старта | высокая | средняя | ниже |
| Инфраструктурная сложность | низкая | средняя | высокая |
| Независимый деплой | нет | частично | да |
| Независимое масштабирование | нет | ограниченно | да |
| Изоляция отказов | слабая | средняя | сильная |
| Чёткость границ данных | зависит от дисциплины | средняя | жёсткая |
| Транзакционная консистентность | ACID | локально ACID | eventual, saga |
| Соответствие требованиям кейса | частичное | частичное | полное |

## 6. Финальный выбор и обоснование

Выбран Вариант C, fine-grained микросервисы по bounded context.

Аргументация опирается на требования кейса и ограничения:

1. Персонализированная лента требует отдельного стека Python с ClickHouse и Redis и асинхронного пересчёта на основе событий. Это плохо ложится на монолит и тащит чужой стек в coarse-сервис.
2. Платежи требуют изоляции, ограниченного доступа, отдельных секретов и аудита. Выделение `payment-service` практически обязательно.
3. Уведомления не должны лежать на критическом пути оформления заказа, это естественный кандидат на отдельный сервис, подписанный на события из Kafka.
4. Каталог read-heavy и нуждается в поисковом индексе и собственном масштабировании. В монолите или coarse это вызывает конкуренцию за ресурсы с транзакционными заказами.
5. Оформление заказа транзакционный домен с собственным жизненным циклом, который удобно реализовать как сагу: OrderCreated, резерв, PaymentCompleted, подтверждение.

Где сознательно идём на компромиссы:

- Принимаем eventual consistency между сервисами и решаем её через transactional outbox, Kafka и саги в `order-service`.
- Принимаем операционные расходы на Kafka, gateway и observability как цену за независимое масштабирование и изоляцию отказов.
- На раннем этапе допустимо начать с более крупных границ и расщеплять их по мере роста. Диаграмма выше отражает целевое состояние.
